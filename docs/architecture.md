# Dualign 工作报告架构

状态：当前实现  
更新日期：2026-08-19

## 产品边界

Dualign 一次处理两份平行文档。文档 A / 文档 B 是中性位置，不隐含“权威原文”和“附属译文”。如果同一作品有三种语言，应按实际需要建立多个独立文档对；系统不通过第三种语言推导传递关系。

Dualign 负责对齐、规则校订、AI 建议、人工审核和显式覆写源文档。作品目录、抓取、翻译任务、部署和阅读器页面由上层应用负责。

## 唯一持久工作状态

每个文档对由三个文件组成：

```text
document-a.md
document-b.md
chapter.report.json
```

`report.json` 是唯一的对齐与校订状态，包含：

- 两份源文档的规范化 SHA-256；
- 对齐模型、算法和非敏感配置来源；
- 不可变初始关系 `ops`；
- 基于原始关系编号的 `repair_log`；
- AI 建议、人工审核状态、评分和覆写历史。

报告不复制完整正文。`RepairState` 总是从原始关系重放操作，因此编辑、撤销和重新编辑不会造成后续关系编号漂移。源文档哈希或模型配置不匹配时，报告失效并要求重新对齐。

旧报告不迁移：发现没有 `format: dualign-report` 的文件时直接提示重新对齐。嵌入向量 SQLite 缓存独立保留，可以显著降低重新生成报告的成本。

## 保存与覆写

- 自动保存和“保存工作报告”只原子更新 JSON，不改写源文档。
- 未选择“覆写源文档”时，磁盘上的两份 Markdown 始终保持原样。
- “覆写源文档”先展示两侧差异，再以可恢复的三文件事务写入文档 A、文档 B 和更新后的报告。
- 覆写前报告中的当前 `repair_log` 会归档到 `history`，随后清空；新正文和新快照形成下一轮基线。
- 备份职责由 Git、文件历史或调用方承担，Dualign 不再生成 `.bak`。

## 阅读器兼容制品

逐行阅读器仍可消费等长的两份 Markdown，但它们不是数据源。构建时调用 `materialize_reader_rows()`，从源文档和报告在临时目录中重放并生成，构建完成立即删除。这样既保留现有阅读器兼容性，也避免长期维护 `repaired/` 副本。

## 明确移除的概念

- 不再隐式导出修订后的 Markdown；
- 不再维护 `repaired/`、`.bak` 或“晋升”流程；
- 不用 YAML 复制 JSON 工作状态；
- 不提供旧报告格式迁移；
- 不把恢复文件与正式对齐数据拆成两套相互同步的权威状态。

## 数据流

```text
文档 A + 文档 B
       │
       ├── 对齐 ──> report.json
       │                 │
       │          校订 / AI / 人工审核
       │                 │
       │          原子保存 report.json
       │                 │
       ├── 明确覆写 <─────┘
       │
       └── 阅读器构建：临时物化等行 Markdown ──> 静态站点
```
